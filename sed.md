# SeD and Pontmore: Discovery, Trust, and Coordination

_Research snapshot: 15 September 2026. SeD is an open, unmerged [Service Discovery Protocol PR](https://github.com/OpenBitcoinAfrica/ServiceDiscoveryProtocol/pull/3) at [`d0c82129`](https://github.com/Extheoisah/ServiceDiscoveryProtocol/commit/d0c82129eb9c24ef2c074c11085d0ab0fc40107e). Pontmore protocol main is [`d9a1eb3e`](https://github.com/pontmore/protocol/commit/d9a1eb3e8a24e2101f5a4024df1ce85a8d934f75), merged on 14 September 2026. This is comparative research, not an adopted integration or a claim of production readiness._

## Executive finding

SeD and Pontmore **partly overlap in capability discovery**, but they address different decisions. SeD tries to locate a B2B service for a corridor and assess its standing through expiring operational signals and a local Web of Trust. Pontmore identifies a versioned Agent capability, describes compatible escrow mechanisms, and validates the signer, authority, linkage, expiry, and economic gates of one bounded coordination. Pontmore expressly does not prove an Agent's availability, solvency, reputation, or external performance. [SeD introduction](https://github.com/Extheoisah/ServiceDiscoveryProtocol/blob/d0c82129eb9c24ef2c074c11085d0ab0fc40107e/00-introduction.md) · [Pontmore README](https://github.com/pontmore/protocol/blob/d9a1eb3e8a24e2101f5a4024df1ce85a8d934f75/README.md)

The plausible composition is an **optional SeD-style signal and trust layer used by a Pontmore application before selecting a counterparty**. It should not become a second canonical Pontmore identity, capability registry, escrow contract, or source of economic truth. An attestation about a Pontmore interaction could cite its immutable event chain, but a signed action is still a signed claim about an external outcome, not proof that fiat arrived or a provider fulfilled an SLA. [Pontmore PIP-00](https://github.com/pontmore/protocol/blob/d9a1eb3e8a24e2101f5a4024df1ce85a8d934f75/PIP-00-agent-definition.md) · [Pontmore PIP-02](https://github.com/pontmore/protocol/blob/d9a1eb3e8a24e2101f5a4024df1ce85a8d934f75/PIP-02-coordination-event-chains.md)

## Scope of the current proposals

| Surface | SeD proposal | Pontmore current draft | Relationship |
| --- | --- | --- | --- |
| Identity | Service identity pubkey (IPK), operational pubkey (OPK), NIP-05 domain authorization and rotation | Nostr Agent pubkey signs the capability definition and participates under root-bound authority | Competing identity roots unless explicitly bound |
| Discovery | Expiring `kind:30078` signal with region, currency, rail, capacity tier, endpoint and heartbeat | Addressable `kind:30360` PIP-00 index of versioned capabilities and applicable descriptor references | Partial overlap: stable capability versus current service conditions |
| Service/escrow description | Generic endpoint advertisement, with API-documentation discussion in PR review | Addressable `kind:30361` PIP-01 escrow compatibility descriptor and optional OpenAPI/AsyncAPI schema | Complementary when the endpoint is generic; duplicate only if both describe the same escrow service inconsistently |
| Reputation | `kind:30079` peer attestations and anchor-distance local trust evaluation | Explicitly application-owned; no reputation score or evidence evaluator in the core | A possible optional input to application selection |
| Interaction state | No standardized bilateral economic coordination chain | Experimental PIP-02 immutable `kind:7300` root and append-only `kind:7301` actions, with profile-defined domain meaning | Pontmore adds a distinct verifiable-history layer |
| Dispute/expiry | Reputation warning and signal/key revocation; expiring availability claim | Root-bound coordination dispute and resolution effects; descriptor selection expiry | Similar words but different objects and timelines |

## Where duplication would hurt

### One capability, two advertisements

PIP-00 is a deliberately small, versioned capability index: `content.capabilities` and filterable tags must agree. It excludes offers, prices, inventory, current availability, and reputation. SeD-02's region/currency/rail/capacity/endpoint signal is more useful for live B2B route selection, but it should not be interpreted as another authoritative declaration that the Agent implements `pontmore/swap@1`. Otherwise a client can encounter divergent, differently expired statements for the same provider. A clean division is **PIP-00 says what protocol/profile the Agent implements; a signed short-lived signal says where and under what current conditions the provider claims to operate**. Neither proves that a live route can complete a payment. [PIP-00](https://github.com/pontmore/protocol/blob/d9a1eb3e8a24e2101f5a4024df1ce85a8d934f75/PIP-00-agent-definition.md) · [SeD-02](https://github.com/Extheoisah/ServiceDiscoveryProtocol/blob/d0c82129eb9c24ef2c074c11085d0ab0fc40107e/SeD-02.md)

SeD currently puts public capability signals in Nostr `kind:30078`. [NIP-78](https://github.com/nostr-protocol/nips/blob/master/78.md) specifies that kind for arbitrary application data rather than generic interoperable interchange, and notes that relays may require authorization to serve it. This is not a cryptographic impossibility, but it is a poor default for a public cross-client discovery protocol. A dedicated kind and shared validation vectors would be a stronger target if SeD seeks Nostr interoperability. [SeD-02](https://github.com/Extheoisah/ServiceDiscoveryProtocol/blob/d0c82129eb9c24ef2c074c11085d0ab0fc40107e/SeD-02.md)

### Two identity authorities

SeD-01's IPK/OPK split is an operationally useful idea: a service can keep its identity key cold while rotating a hot signer for heartbeat signals. Pontmore, however, binds its public Agent definition and coordination participants/authorities to Nostr pubkeys. Treating a rotating OPK as the Pontmore Agent would change the visible identity on every rotation; treating a NIP-05 DNS record as the sole Pontmore authority would make DNS compromise sufficient to substitute the service. [NIP-05](https://github.com/nostr-protocol/nips/blob/master/05.md) frames domain lookup as identification, not verification. An integration must define an IPK-to-Pontmore-Agent binding signed by the appropriate key, its scope and expiry, rotation/revocation semantics, and how existing coordination roots remain bound to their accepted keys. Merely seeing the same domain or label in both profiles is not enough. [SeD-01](https://github.com/Extheoisah/ServiceDiscoveryProtocol/blob/d0c82129eb9c24ef2c074c11085d0ab0fc40107e/SeD-01.md) · [SeD-05](https://github.com/Extheoisah/ServiceDiscoveryProtocol/blob/d0c82129eb9c24ef2c074c11085d0ab0fc40107e/SeD-05.md) · [PIP-02](https://github.com/pontmore/protocol/blob/d9a1eb3e8a24e2101f5a4024df1ce85a8d934f75/PIP-02-coordination-event-chains.md)

### Endpoints are not escrow contracts

SeD-02 advertises a generic service endpoint. Its [PR review](https://github.com/OpenBitcoinAfrica/ServiceDiscoveryProtocol/pull/3#discussion_r3566031860) discusses an API-documentation pointer, and a [cross-proposal comment](https://github.com/OpenBitcoinAfrica/ServiceDiscoveryProtocol/pull/3#discussion_r3941741168) points to Pontmore's schema approach. PIP-01's optional `service.schema` is narrower: an OpenAPI/AsyncAPI reference for an **escrow mechanism**, with fetch safety and validation requirements. Its descriptor is not itself a funding/release/refund contract. SeD could borrow schema discovery for generic B2B interfaces without making every generic service a PIP-01 escrow or duplicating escrow operations in a signal. [PIP-01](https://github.com/pontmore/protocol/blob/d9a1eb3e8a24e2101f5a4024df1ce85a8d934f75/PIP-01-escrow-descriptor.md)

## Where composition could add value

1. **Pre-coordination selection.** An application can combine a valid PIP-00 capability, an unexpired PIP-01 descriptor if escrow is needed, and SeD-style expiring corridor/rail/capacity claims. It can then challenge or quote the service before committing. Dynamic claims should not be frozen into PIP-00 simply because they are useful to matchmakers. [PIP-00](https://github.com/pontmore/protocol/blob/d9a1eb3e8a24e2101f5a4024df1ce85a8d934f75/PIP-00-agent-definition.md) · [PIP-01](https://github.com/pontmore/protocol/blob/d9a1eb3e8a24e2101f5a4024df1ce85a8d934f75/PIP-01-escrow-descriptor.md)
2. **Interaction-referenced attestations.** An attester could cite a specific immutable PIP-02 root, final action, profile, role, amount band, and independently verifiable receipt or evidence commitment. This would make the claim inspectable, while keeping private banking or service evidence out of public event content. PIP-02 validates action authorship and sequence, not the external truth of settlement; the attester's scope and evidence still need local evaluation. [SeD-03](https://github.com/Extheoisah/ServiceDiscoveryProtocol/blob/d0c82129eb9c24ef2c074c11085d0ab0fc40107e/SeD-03.md) · [PIP-02](https://github.com/pontmore/protocol/blob/d9a1eb3e8a24e2101f5a4024df1ce85a8d934f75/PIP-02-coordination-event-chains.md)
3. **Operational key practice.** SeD's cold identity/hot operational key distinction and revocation work can inform a Pontmore service deployment, provided delegation and key changes are explicitly authorized and never retroactively rewrite an accepted coordination. [SeD-01](https://github.com/Extheoisah/ServiceDiscoveryProtocol/blob/d0c82129eb9c24ef2c074c11085d0ab0fc40107e/SeD-01.md) · [SeD-05](https://github.com/Extheoisah/ServiceDiscoveryProtocol/blob/d0c82129eb9c24ef2c074c11085d0ab0fc40107e/SeD-05.md) · [PIP-02](https://github.com/pontmore/protocol/blob/d9a1eb3e8a24e2101f5a4024df1ce85a8d934f75/PIP-02-coordination-event-chains.md)
4. **Local trust policy.** SeD-06's anchor-distance graph could help a client order candidates. It is a filter for disconnected attestations, not a proof of honesty: direct anchors can still attest falsely, and anchored Sybil accounts can still collude. Reliability should depend on issuer competence, claim scope, recency, independently checkable evidence, and the client's own risk policy, not graph distance alone. [SeD-06](https://github.com/Extheoisah/ServiceDiscoveryProtocol/blob/d0c82129eb9c24ef2c074c11085d0ab0fc40107e/SeD-06.md)

SeD-03 currently uses a replaceable `d` address per subject and attestation type. That favors latest-status lookup but does not guarantee retained history on a relay. An [open review suggestion](https://github.com/OpenBitcoinAfrica/ServiceDiscoveryProtocol/pull/3#discussion_r3854212031) proposes unique attestation instances plus a replaceable head pointer. Such an append-only history would compose better with Pontmore's immutable coordination chain; it remains a proposal, not merged SeD behavior. Private attestations also need a concrete recipient/group-key, rotation, access and metadata-leakage design. SeD's current consortium-encryption explanation is not yet an interoperable privacy protocol. [SeD-03](https://github.com/Extheoisah/ServiceDiscoveryProtocol/blob/d0c82129eb9c24ef2c074c11085d0ab0fc40107e/SeD-03.md) · [privacy review thread](https://github.com/OpenBitcoinAfrica/ServiceDiscoveryProtocol/pull/3#discussion_r3565980256)

## Maturity comparison

| Evidence as of 15 September 2026 | SeD | Pontmore |
| --- | --- | --- |
| Specification status | Seven-document proposal in an open, unmerged PR; its base repository does not yet adopt those documents | Three PIPs merged on main through [PR #20](https://github.com/pontmore/protocol/pull/20); conformance profiles defined |
| Runnable implementation | No implementation or conformance suite visible in the proposal repository | [Rust reference implementation](https://github.com/pontmore/pontmore/blob/a19e4a0b4b400594b953c8db9332a50bb8a32bc9/README.md) with signed-event validation, daemon/relay integration, a simulated no-value connector, and [test vectors](https://github.com/pontmore/pontmore/tree/a19e4a0b4b400594b953c8db9332a50bb8a32bc9/tck/vectors) |
| Independent interoperability | Not demonstrated | Not yet demonstrated for generalized PIP-02 or `pontmore/swap@1`; its own profile disclaims an interoperability claim |
| Production/economic assurance | No deployment or economic-operation evidence in the proposal | Reference code exists, but real-value connectors, reviewed policies, hardened ingress/sandboxing, independent implementations and broader profile validation remain work |

Pontmore is **more mature in committed specification and executable validation**, not a finished standard or production assurance. SeD is **proposal-stage**, though it offers a more concrete vocabulary for dynamic B2B corridor discovery. The comparison should not mistake Pontmore's reference implementation for independent interoperability, or SeD's signed attestations for verified economic outcomes. [SeD PR](https://github.com/OpenBitcoinAfrica/ServiceDiscoveryProtocol/pull/3) · [Pontmore README](https://github.com/pontmore/protocol/blob/d9a1eb3e8a24e2101f5a4024df1ce85a8d934f75/README.md) · [`pontmore/swap@1`](https://github.com/pontmore/protocol/blob/d9a1eb3e8a24e2101f5a4024df1ce85a8d934f75/profiles/swap-v1.md) · [implementation README](https://github.com/pontmore/pontmore/blob/a19e4a0b4b400594b953c8db9332a50bb8a32bc9/README.md)

## Smallest useful joint experiment

Define one test corridor and two provider keys. Publish a Pontmore PIP-00 capability and, separately, a short-lived SeD-style availability signal cryptographically bound to the same provider. Bind an accepted quote and escrow descriptor revision in a `pontmore/swap@1` coordination; then publish an attestation that references its immutable outcome plus a verifier-checkable, privacy-preserving evidence commitment. Give two independently written clients fixtures for key rotation, stale signals, conflicting attestations, missing evidence, forks, and descriptor expiry. Require them to agree on **protocol validity** while allowing different **local trust decisions**. This tests the real complement without expanding Pontmore's economic kernel or assuming SeD's trust claims are protocol truth.
